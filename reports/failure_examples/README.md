# Failure case examples

Three renders from `reports/failures/` (25 total, generated by
`scripts/mine_failures.py`, `.gitignore`'d as a full set since they're
large — these three are picked out and tracked here as the actual
evidence behind the memo's failure analysis). Ground truth on the left,
prediction on the right, both with class name and confidence drawn on
each box.

## `dense_entries_financial_report.png`

Source: `test_000035`, financial_reports, the worst page overall (38
missed, 82 false positives). A bank's organizational directory — ~25
near-identical repeated `Section-header`/`Text` entry pairs stacked in
two columns. Ground truth has one clean box per entry; the prediction
shows heavily overlapping, offset duplicate boxes at scattered
confidence (0.25–0.85). The model can't cleanly separate many
visually near-identical, tightly packed instances.

## `composite_picture_fragmentation.png`

Source: `test_000425`, patents (0 missed, 0 misclassified, 61 false
positives — the cleanest signature in the run). Each ground-truth
`Picture` is one chemical structure diagram; the model predicts 2–3
overlapping `Picture` boxes per diagram instead of one, treating the
diagram's internal sub-drawing and inline formula text as separable
parts. Directly explains `Picture`'s low precision (0.416) despite
reasonable recall (0.622).

## `dense_entries_scientific_article.png`

Source: `test_000447`, scientific_articles. The same dense-repeated-entry
failure as the financial report above, but in a different document type
and on different content: a reference list gets fragmented into
overlapping duplicate `List-item` boxes, and individual multi-line
`Formula` blocks get split into overlapping `Formula`/`List-item`
fragments instead of one box per equation. Confirms the failure is a
general limitation of the fixed-query architecture on dense, repetitive
layouts — not a one-off quirk of the financial-report case.
